# 1. 执行摘要

## 1.1 审计目的

ICA-RUST 已经具备独立 Rust 后端工程基础。本阶段工作的重点不再是验证 Rust 是否能够实现 ICA，而是评估现有 Rust 工程是否具备承接 ICA 产品业务、完成 MVP 功能闭环和正式交付的能力。

本次审计重点回答五个问题：

1. ICA-RUST 当前已经实现了哪些产品功能？
2. 哪些模块虽然已经实现，但还没有达到产品交付质量？
3. 与 Python 基线相比，是否存在业务行为、数据模型和 API 契约差异？
4. 距离 ICA MVP 完整交付还缺少哪些能力？
5. 如何在不重复开发、不破坏现有成果的前提下完成产品化？

## 1.2 核心结论

本项目采用以下技术与工程方向：

**Rust-First Product Architecture**

- ICA-RUST：正式业务后端。
- React + TypeScript：前端 GUI。
- Tauri 2 + Rust：桌面运行环境。
- SQLite：本地业务数据库。
- Hermes Agent：独立 Agent Runtime。
- MCP：Agent 与 ICA 的标准化业务接口。
- Python：按需保留 OCR、文档解析及其他专项能力。

Python 不再作为默认业务后端，但其历史实现仍然是重要的业务行为参考。

## 1.3 产品化目标

ICA MVP 必须能够支持一名招聘人员独立完成以下业务闭环：

招聘项目管理 → 岗位管理 → 候选人管理 → 应聘管理 → 沟通记录 → 跟进任务 → AI 辅助沟通 → 人工审核与执行。

产品化验收不能只依据 API 数量、代码行数或测试数量。

必须同时满足：

- 领域模型正确。
- 业务流程完整。
- API 契约稳定。
- GUI 可以完成实际操作。
- 数据安全可靠。
- 离线业务可用。
- 安装包能够独立运行。
- 异常场景能够正确恢复。

# 3. MVP 产品范围

## 3.1 产品定位

ICA 是面向房地产交易企业内部招聘人员的 AI-native Recruitment Workspace。

核心定位：

通过本地优先的数据管理、结构化招聘工作流和 AI 辅助能力，提高招聘人员的日常工作效率。

产品核心不是通用聊天机器人，而是招聘业务工作台。

## 3.2 MVP 必须具备的业务模块

| 模块 | 核心功能 | 优先级 |
|---|---|---|
| Dashboard | 招聘概览、待办、活动记录 | P0 |
| Projects | 招聘项目管理 | P0 |
| Positions | 岗位管理 | P0 |
| Candidates | 候选人档案管理 | P0 |
| Applications | 候选人应聘记录与阶段管理 | P0 |
| Conversations | 沟通历史 | P0 |
| Follow-ups | 跟进任务和提醒 | P0 |
| AI Assistant | 招聘上下文和沟通辅助 | P0 |
| Settings | 本地配置与 AI 配置 | P0 |
| Data Management | 备份、恢复、导入、导出 | P0 |
| Audit | 关键操作追踪 | P1 |
| Sharing | 外部数据分享 | 暂缓评估 |

## 3.3 核心领域模型

必须确保以下实体边界清晰：

### Candidate

候选人主体。

一个候选人可以与多个岗位建立应聘关系。

### Position

招聘岗位。

岗位归属于招聘项目，承载岗位要求和招聘状态。

### Application

候选人针对特定岗位的一次应聘记录。

这是招聘业务的核心关联实体。

必须支持：

- Candidate 与 Position 的多对多业务关系。
- 独立的应聘阶段。
- 应聘状态变更记录。
- 结束原因。
- 应聘历史。

不能将 Candidate 的全局状态与 Application 的岗位应聘状态混为一谈。

### Conversation

候选人与招聘人员之间的沟通上下文。

### Follow-up

与候选人或具体 Application 关联的后续任务。

### AI Draft

AI 生成的沟通草稿。

必须保留人工审核和确认机制。

## 4.2 架构职责

| 组件 | 主要职责 | 不应承担的职责 |
|---|---|---|
| React | UI、用户交互 | 直接访问数据库 |
| Tauri Host | 桌面运行管理 | 重复实现招聘业务 |
| Rust Backend | 招聘领域与业务 API | Agent 自主决策 |
| SQLite | 本地持久化 | 业务规则判断 |
| Hermes | Agent 推理和任务执行 | 绕过 ICA 直接修改业务库 |
| Browser | 受控外部交互 | 未授权自动操作 |
| Python Services | 专项处理 | 重复实现完整业务后端 |

## 4.3 架构验收要求

- Domain 不依赖具体 HTTP 框架。
- Application 层负责业务用例编排。
- Infrastructure 层负责数据库和外部依赖。
- API 层只负责协议转换和请求处理。
- GUI 不直接访问 SQLite。
- Agent 通过受控 API 或 MCP 操作业务。
- 关键业务操作具备事务一致性。
- 数据库迁移具备版本管理和回滚策略。

# 6. Python 与 Rust 契约差异审计

## 6.1 基线原则

Python 项目 `9ed173c` 作为历史行为参考。

Rust 项目不要求逐行复制 Python 实现，而是要求保持经过确认的业务语义和外部契约。

如果 Python 存在历史缺陷，应通过明确的 ADR 记录修正，而不是将缺陷机械迁移到 Rust。

## 6.2 差异审计内容

| 类别 | 核查内容 |
|---|---|
| Domain | 实体、关系、状态定义 |
| API | 请求和响应 |
| Database | Schema、约束和索引 |
| Validation | 输入校验 |
| Business Rule | 业务规则 |
| Error | 错误码和错误信息 |
| Time | 日期、时区和时间精度 |
| Import | 导入冲突处理 |
| OCR | 识别结果与数据转换 |
| Dashboard | 聚合和统计逻辑 |

## 6.3 差异处理策略

每项差异必须归类：

- COMPATIBLE：行为一致。
- INTENTIONAL：经过批准的主动调整。
- BUG：Rust 实现缺陷。
- BASELINE_BUG：Python 历史缺陷。
- UNRESOLVED：尚未确认。

禁止通过忽略测试差异来宣告迁移完成。

## 6.4 契约回放

需要建立统一的测试输入与输出样本。

```text
Contract Replay
│
├── Input Fixtures
│
├── Python Baseline
│   └── Expected Behavior
│
├── Rust Implementation
│   └── Actual Behavior
│
└── Diff Engine
    ├── Match
    ├── Intentional Difference
    └── Regression
```

要求：

- 测试数据固定。
- 测试环境隔离。
- 排除无意义的动态字段差异。
- 关键业务结果必须一致。
- 所有允许差异均有记录。

# 12. 最终决策

## 12.1 技术决策

确定采用 Rust-First 产品架构。

Rust 负责正式业务后端和桌面系统能力；React 负责 GUI；Hermes 负责 Agent Runtime；Python 仅在必要的专项能力中保留。

## 12.2 工程决策

不进行无必要的整体重写。

不以代码行数和模块数量作为产品化完成标准。

不因引入 Hermes 而重复建设 Agent Runtime。

不让 Agent 绕过 ICA 业务接口操作数据库。

不在 MVP 阶段引入未经验证的浏览器自动化和复杂云端能力。

## 12.3 实施决策

严格按照以下顺序推进：

```text
工程基线冻结
      ↓
领域模型审计
      ↓
数据与契约闭合
      ↓
核心招聘业务闭环
      ↓
AI 能力产品化
      ↓
GUI 联调
      ↓
安全与交付
      ↓
MVP 验收
      ↓
Hermes Agent 集成
      ↓
浏览器与云端扩展
```

## 12.4 最终目标

ICA-RUST 的最终目标不是成为一个单纯的 Rust 后端工程，而是成为 ICA 产品的稳定业务核心。

**产品目标：一个招聘人员能够依靠 ICA 独立完成日常招聘管理和沟通工作的 AI-native Recruitment Workspace。**

**工程目标：建立可测试、可维护、可扩展、可交付的 Rust-Native Desktop Application。**

**长期目标：通过 Hermes Agent、MCP 和受控浏览器能力，将 ICA 从招聘管理工作台逐步升级为招聘 Agent 工作平台。**
