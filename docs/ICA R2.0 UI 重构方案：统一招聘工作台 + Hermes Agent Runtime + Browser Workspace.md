# 1. 文档概述

## 1.1 编写目的

本文档定义 ICA Personal UI/UX 2.0 的总体设计方向、信息架构、视觉设计体系、交互规范、前端工程架构及分阶段重构实施计划。

本次 UI 重构不是单纯的视觉优化，而是面向 ICA 产品定位、业务工作流和未来 Agent 扩展能力的一次整体交互架构升级。

主要解决以下问题：

1. 现有界面采用传统后台管理系统布局，缺少统一的桌面工作空间设计。
2. 一级导航与二级导航之间缺乏统一的信息架构。
3. 系统设置中的 AI Provider、模型管理、场景路由等功能耦合度较高。
4. 业务操作、AI 辅助操作和 Agent 执行之间缺少清晰的交互边界。
5. 缺少统一的 Design System 和前端组件规范。
6. 现有 UI 对未来 Hermes Agent、MCP 和浏览器子系统的扩展支持不足。

## 1.2 设计目标

| 目标      | 具体要求                      |
| ------- | ------------------------- |
| 统一视觉体系  | 建立完整的 Design Tokens 和组件规范 |
| 优化信息架构  | 统一一级导航、二级导航和页面组织          |
| AI 原生交互 | 将 AI 助手融入招聘业务工作流          |
| 业务效率    | 减少页面跳转和重复操作               |
| 配置可视化   | 提升 AI 服务、模型和路由的可理解性       |
| 安全性     | 明确 AI、Agent 和人工操作权限边界     |
| 可扩展性    | 支持 Hermes、MCP 和浏览器子系统     |
| 本地优先    | 不破坏现有 Rust 后端和本地数据架构      |

## 1.3 非目标

本次 UI 重构不意味着同步扩大 MVP 产品范围。

以下事项不属于 UI 2.0 首期交付范围：

- 自动向候选人发送招聘消息。
- 自动执行完整招聘流程。
- 自动修改候选人业务数据。
- 自研完整 Agent Runtime。
- 自研浏览器自动化引擎。
- 引入在线服务作为 ICA 正常运行的必要条件。
- 改变现有 Rust 后端核心业务模型。
- 因 UI 重构而迁移或重建现有数据库。

# 2. 产品定位与设计原则

## 2.1 产品定位

ICA Personal 是一款面向个人招聘工作流的本地优先 AI 招聘工作台。

核心定位：

**以招聘业务为中心，以 AI 助手为智能协作入口，以人工审核为最终控制机制。**

产品不应被设计成传统 CRM，也不应简单地成为一个 AI Chat 客户端。

核心能力包括：

1. 招聘业务管理。
2. 候选人信息管理。
3. 岗位需求管理。
4. 招聘沟通记录。
5. 招聘跟进任务。
6. AI 辅助分析和内容生成。
7. AI 草稿人工审核。
8. Agent 和浏览器能力扩展。

## 2.2 核心设计原则

### P1：Business-first

所有主要交互围绕招聘业务展开。

AI 能力应该服务于候选人管理、岗位分析、沟通和跟进，而不是让用户脱离业务上下文单独使用 AI。

### P2：AI-native

AI 不是独立附加功能，而是融入业务工作流的协作能力。

例如：

- 在候选人页面调用 AI 分析。
- 在岗位页面调用 AI 分析 JD。
- 在沟通记录中生成回复草稿。
- 在跟进任务中生成行动建议。

### P3：Human-in-the-loop

所有具有外部影响或业务写入风险的操作必须保留人工控制。

特别是：

- 候选人信息修改。
- 招聘沟通内容发送。
- 招聘状态变更。
- Agent 执行外部操作。

### P4：Local-first

核心业务数据保存在本地。

AI 服务不可用时，仍应允许用户访问和管理本地业务数据。

### P5：Offline-first

不依赖云端服务才能启动和使用核心功能。

在线 AI、外部 Agent 和浏览器能力属于可选扩展。

### P6：Modular Architecture

前端按照业务模块划分，避免形成大型页面组件和全局状态耦合。

### P7：Consistent Experience

统一导航、组件、状态、反馈、布局和交互方式。

# 3. 整体 UI 信息架构

## 3.1 一级导航设计

建议将现有一级导航重新整理为四个功能区域。

| 一级区域    | 页面      | 功能定位              |
| ------- | ------- | ----------------- |
| 工作空间    | 工作台     | 招聘工作总览            |
| 工作空间    | 招聘项目    | 招聘任务组织（如现有业务模型支持） |
| 工作空间    | 候选人     | 候选人信息管理           |
| 工作空间    | 岗位管理    | 招聘岗位管理            |
| 工作空间    | 沟通记录    | 沟通历史管理            |
| 工作空间    | 跟进任务    | 招聘跟进管理            |
| AI 工作空间 | AI 助手   | AI 交互与业务协作        |
| AI 工作空间 | AI 草稿审核 | AI 生成内容审核         |
| AI 工作空间 | 浏览器工作区  | 浏览器能力入口           |
| 系统管理    | 系统设置    | 应用配置管理            |
| 系统管理    | 安全与审计   | 权限和操作记录           |

说明：

1. 不应为了导航完整而提前实现尚未具备的业务功能。
2. 招聘项目如没有独立领域模型，可以先使用现有业务页面组织方式，不应强制增加新实体。
3. 安全与审计可以先作为系统设置中的子页面，待功能成熟后再独立导航。

## 3.2 系统设置二级导航

建议将现有系统设置重新组织为以下结构：

### 系统配置

| 页面      | 主要内容                      |
| ------- | ------------------------- |
| 通用设置    | 应用语言、主题、界面偏好              |
| AI 服务连接 | Provider、Endpoint、API Key |
| 模型管理    | 模型注册、能力、默认模型              |
| 场景路由    | 业务场景与模型映射                 |
| 隐私与安全   | 敏感信息、AI 数据传输策略            |
| 数据与备份   | 数据存储、备份、恢复                |

### 运行管理

| 页面        | 主要内容             |
| --------- | ---------------- |
| Agent 运行时 | Agent 状态、连接和执行管理 |
| 浏览器管理     | 浏览器实例、会话及运行状态    |
| 权限管理      | 工具授权和操作权限        |
| 审计日志      | 操作事件、执行记录和异常     |

Agent 运行时和浏览器管理属于后续扩展页面，首期可以仅展示已实现能力。

## 3.3 导航交互规范

- 一级导航固定在窗口左侧。
- 二级导航根据当前模块显示。
- 当前页面具有明显选中状态。
- 支持导航折叠。
- 页面切换不应导致整个 App Shell 重新加载。
- 支持窗口尺寸变化。
- 支持键盘焦点和快捷导航。
- 页面标题与面包屑保持一致。

# 4. 整体布局架构

## 4.1 App Shell

采用统一的桌面应用外壳。

整体结构：

```
┌──────────────────────────────────────────────────────────────┐
│                     Window / Title Bar                       │
├───────────────┬──────────────────────────────────────────────┤
│               │                                              │
│               │              Page Header                     │
│               │                                              │
│  Primary      ├──────────────────────────────────────────────┤
│  Sidebar      │                                              │
│               │                                              │
│               │              Main Content                    │
│               │                                              │
│               │                                              │
│               │                                              │
│               │                                              │
│               │                                              │
├───────────────┴──────────────────────────────────────────────┤
│                    Status / Feedback Area                    │
└──────────────────────────────────────────────────────────────┘
```

App Shell 负责：

- 全局导航。
- 页面容器。
- 主题管理。
- 全局快捷操作。
- 消息通知。
- 全局状态反馈。
- AI 助手面板入口。

业务页面不得重复实现这些基础能力。

## 4.2 三栏工作空间

针对 AI 工作空间，采用可选三栏布局。

```
┌────────────┬─────────────────────────┬─────────────────────┐
│            │                         │                     │
│ Navigation │     Business Context    │    AI Assistant     │
│            │                         │                     │
│            │                         │                     │
│            │                         │    AI Conversation  │
│            │                         │                     │
│            │                         │                     │
│            │                         │    Suggestions      │
│            │                         │                     │
│            │                         │    Drafts            │
│            │                         │                     │
└────────────┴─────────────────────────┴─────────────────────┘
```

各区域职责：

| 区域 | 职责         |
| -- | ---------- |
| 左侧 | 导航和工作入口    |
| 中间 | 当前招聘业务内容   |
| 右侧 | AI 助手和智能协作 |

右侧 AI 面板应支持：

- 展开和折叠。
- 调整宽度。
- 显示当前业务上下文。
- 查看 AI 生成结果。
- 查看工具执行结果。
- 生成草稿。
- 提交人工审核。

普通业务页面不强制显示右侧面板，避免影响内容空间。

## 4.3 布局尺寸

建议采用以下初始设计参数：

| 区域       | 推荐尺寸      |

| 一级导航     | 220～240px |
| 二级导航     | 190～210px |
| 页面内容区    | 自适应       |
| AI 面板    | 320～400px |
| 页面最大内容宽度 | 1320px    |
| 页面内边距    | 24～32px   |
| 卡片间距     | 16～24px   |

尺寸为设计建议，应通过 Windows 实际窗口测试调整。

# 6. 核心页面 UI 设计

## 6.1 工作台 Dashboard

定位：招聘工作的统一入口。

主要展示：

- 当前招聘工作概览。
- 候选人数量。
- 待跟进任务。
- 最近沟通记录。
- 最近使用的岗位。
- AI 工作建议。
- 最近操作。

页面布局：

```
┌────────────────────────────────────────────┐
│ 工作台                  日期 / 快捷操作    │
├────────────────────────────────────────────┤
│ 候选人数量 │ 岗位数量 │ 待跟进 │ 待审核     │
├──────────────────────────┬─────────────────┤
│                          │                 │
│ 最近招聘活动             │ AI 工作建议     │
│                          │                 │
├──────────────────────────┴─────────────────┤
│ 最近候选人                                 │
├────────────────────────────────────────────┤
│ 最近沟通与任务                             │
└────────────────────────────────────────────┘
```

指标必须来自真实业务数据，不能使用模拟数据冒充实际统计。

## 6.2 候选人管理

定位：候选人信息管理与招聘分析入口。

主要区域：

1. 候选人搜索和筛选。
2. 候选人列表。
3. 候选人基本信息。
4. 候选人沟通记录。
5. 候选人跟进任务。
6. AI 辅助分析。

候选人详情建议采用 Tabs：

- 基本信息。
- 工作经历。
- 招聘沟通。
- 跟进记录。
- AI 分析。

AI 分析必须能够区分原始数据、AI 推断和用户确认信息。

## 6.3 岗位管理

定位：招聘岗位需求管理。

主要内容：

- 岗位基本信息。
- JD 内容。
- 技能要求。
- 岗位状态。
- 关联候选人。
- AI JD 分析。

AI 分析结果应支持用户确认后再保存为正式业务数据。

## 6.4 沟通记录

定位：招聘沟通历史的统一管理。

采用时间线或列表布局。

展示：

- 沟通对象。
- 沟通时间。
- 沟通渠道。
- 沟通内容。
- 关联候选人。
- 沟通结果。

AI 可以辅助总结和生成回复草稿，但不得默认发送消息。

## 6.5 跟进任务

定位：招聘工作执行管理。

建议支持：

- 待处理。
- 进行中。
- 已完成。
- 已取消。

提供列表视图和日历式视图的扩展能力。

任务状态必须与现有 Rust 领域模型保持一致。

## 6.6 AI 助手

定位：跨业务模块的智能协作入口。

核心能力：

- 自然语言交互。
- 当前业务上下文识别。
- 候选人分析。
- JD 分析。
- 沟通草稿生成。
- 跟进建议。
- 工具调用。
- 执行结果展示。

AI 助手需要显示：

1. 当前使用模型。
2. 当前业务上下文。
3. 当前任务状态。
4. 工具调用状态。
5. 生成结果。
6. 人工审核入口。

AI 生成内容必须具有明确的状态，例如：

- Generating。
- Completed。
- Failed。
- Pending Review。
- Approved。
- Rejected。

其中 Approved 仅表示人工批准，不代表消息已经发送。

## 6.7 AI 草稿审核

定位：AI 生成内容的人工审核中心。

推荐布局：

```
┌─────────────────────────────────────────────┐
│ AI 草稿审核                                  │
├─────────────────────────────────────────────┤
│ 待审核 │ 已批准 │ 已拒绝 │ 全部             │
├──────────────────────┬──────────────────────┤
│ 草稿列表             │ 草稿详情             │
│                      │                      │
│ 候选人 A             │ 原始上下文           │
│ 沟通回复草稿         │                      │
│                      │ AI 生成内容          │
│ 候选人 B             │                      │
│ 分析草稿             │ 编辑区域             │
│                      │                      │
│                      │ 批准 / 拒绝          │
└──────────────────────┴──────────────────────┘
```

必须区分：

- AI 生成。
- 人工编辑。
- 人工批准。
- 外部发送。

MVP 阶段不开放自动发送。

## 6.8 浏览器工作区

浏览器工作区属于后续扩展能力。

UI 可以预留独立入口，但实际操作必须依赖已经实现的 Browser Runtime。

建议包含：

- 浏览器实例状态。
- 当前会话。
- 页面访问状态。
- 操作记录。
- 权限提示。
- 人工确认。

浏览器自动化不得绕过现有业务权限和人工审核机制。

## 7.2 AI 服务连接

拆分为独立页面。

展示内容：

| 字段                   | 说明     |
| -------------------- | ------ |
| Provider             | 服务提供商  |
| Endpoint             | API 地址 |
| API Key              | 敏感凭据   |
| Connection Status    | 连接状态   |
| Configuration Source | 配置来源   |
| Last Test            | 最近测试时间 |

必须支持：

- 新增连接。
- 编辑连接。
- 删除连接。
- 测试连接。
- 启用和禁用。
- 配置来源展示。

安全要求：

- API Key 不得明文回显。
- 日志不得输出完整凭据。
- 前端不持久化明文密钥。
- 密钥修改和清除应有明确确认。
- 配置来源必须可追溯。

## 7.3 模型管理

建议使用模型列表 + 详情面板。

模型元数据包括：

```
Model
├── id
├── provider_id
├── model_identifier
├── display_name
├── tier
├── capabilities
├── enabled
├── is_default
└── configuration_source
```

以上是建议的数据概念，不代表要求直接修改现有数据库 Schema。

模型能力：

- Text Generation。
- Tool Calling。
- JSON Output。
- Vision。
- Streaming。

能力应来源于可信模型元数据或验证结果。

## 7.4 场景路由

场景路由负责将业务请求映射到模型或模型层级。

建议场景：

| 场景         | 推荐层级     |
| ---------- | -------- |
| JD 分析      | Standard |
| 简历分析       | Standard |
| 沟通草稿       | Economy  |
| 深度候选人分析    | Premium  |
| Agent 任务规划 | Premium  |

上述仅为默认策略建议，最终模型选择取决于模型能力、成本和实际测试结果。

UI 需要展示：

- 场景名称。
- 使用模型层级。
- 实际解析模型。
- 默认路由。
- 覆盖规则。
- 配置验证状态。

空值继承默认策略时，需要明确展示继承关系。

## 7.5 隐私与安全

主要配置：

- AI 数据出站策略。
- 敏感信息处理。
- 本地数据访问。
- Agent 工具权限。
- 操作确认策略。

涉及个人信息的数据出站必须有明确的用户授权和提示。

## 7.6 数据与备份

主要功能：

- 数据存储位置。
- 数据库状态。
- 创建备份。
- 恢复备份。
- 最近备份时间。
- 备份校验。
- 恢复前确认。

备份恢复不能仅凭文件存在就判定成功，必须执行完整性校验。

## 7.7 Agent 运行时

作为未来 Hermes Agent 集成入口。

展示：

- Agent 类型。
- Runtime 状态。
- 连接状态。
- 当前执行任务。
- 能力清单。
- 工具权限。
- 执行日志。

ICA 与 Hermes 应通过正式定义的集成接口通信，不允许 UI 直接操纵 Hermes 内部数据文件。

## 8.3 组件设计原则

### 原则一：业务组件与基础组件分离

基础组件不包含招聘业务逻辑。

### 原则二：页面组件不直接访问数据库

页面通过 Feature Service 或统一 API Adapter 调用后端。

### 原则三：统一管理 UI 状态

合理区分：

- 全局 UI 状态。
- 页面状态。
- 业务数据状态。
- 异步请求状态。

不应将所有状态都放入全局 Store。

### 原则四：类型安全

前后端数据契约应明确，避免使用大量 `any`。

### 原则五：错误处理统一

统一处理：

- Tauri Command 错误。
- 业务验证错误。
- 网络错误。
- Provider 错误。
- Runtime 错误。

- 在 UI 中硬编码 Provider 密钥。
- 将外部 Agent 的运行状态伪装为 ICA 内部状态。

# 9. UI 交互规范

## 9.1 页面状态

每个页面必须考虑以下状态：

| 状态       | 表现        |
| -------- | --------- |
| Loading  | 加载反馈      |
| Empty    | 空状态和引导操作  |
| Success  | 正常内容      |
| Error    | 错误信息和恢复建议 |
| Disabled | 禁用状态和原因   |
| Partial  | 部分数据不可用   |

不能只设计正常数据状态。

## 9.2 操作反馈

统一提供：

- Toast。
- Inline Feedback。
- Dialog。
- Drawer。
- Loading Indicator。
- Progress Indicator。

反馈信息应说明实际结果。

例如：

错误：保存成功。

正确：AI 服务配置已保存，尚未完成连接验证。

## 9.3 危险操作

以下操作必须二次确认：

- 删除模型配置。
- 删除 Provider。
- 恢复数据库。
- 清除数据。
- 撤销授权。
- 执行具有外部影响的 Agent 操作。

## 9.4 键盘操作

建议支持：

| 快捷键      | 操作          |
| -------- | ----------- |
| Ctrl + K | 全局命令搜索      |
| Ctrl + , | 打开系统设置      |
| Ctrl + N | 新建当前模块支持的对象 |
| Esc      | 关闭弹窗或侧边面板   |

快捷键必须避免与 Windows 系统及输入法常用操作冲突。

# 10. AI 与 Agent 交互设计

## 10.1 AI 助手与业务上下文

AI 助手应能够感知当前业务上下文。

例如：

```
当前页面：候选人详情
当前对象：Candidate #123
当前操作：分析候选人

AI Context
├── Candidate Information
├── Position Information
├── Communication History
└── User Instructions
```

上下文传递应遵循最小必要原则。

不得默认将全部招聘数据库内容发送给 AI Provider。

## 10.2 AI 操作权限分级

建议建立以下操作等级：

| 等级 | 操作       | 处理方式    |
| -- | -------- | ------- |
| L0 | 信息读取     | 按授权读取   |
| L1 | 分析与总结    | 展示结果    |
| L2 | 生成业务草稿   | 人工审核    |
| L3 | 修改本地业务数据 | 明确确认    |
| L4 | 外部系统操作   | 单独授权和确认 |

此分级为 UI 与权限设计建议，实际执行必须由 Rust 后端进行授权校验。

## 10.3 Hermes Agent 集成

未来采用 Embedded + Hybrid 的集成方向。

UI 负责：

- 展示 Agent 状态。
- 发起经过授权的任务。
- 显示任务执行过程。
- 展示工具调用结果。
- 提供中止和确认入口。

Rust 负责：

- Agent 集成接口。
- 任务生命周期管理。
- 权限检查。
- 数据传递。
- 执行结果处理。

Hermes 负责：

- Agent 任务执行。
- Skill 调用。
- 工具编排。
- 任务推理。

不应将 Hermes 的内部运行机制直接耦合到 React 组件中。
