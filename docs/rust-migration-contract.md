# Rust migration contract — ICA Personal backend

This document is the map for moving the ICA Personal backend HTTP/data plane
from Python (FastAPI + SQLAlchemy) to Rust (axum + sqlx), one wave at a time.

- **Contract authority**: the Python baseline at `/mnt/o/ica` @ `d39e321`. Where
  this document and the Python code disagree, the Python code wins until a wave
  explicitly changes it.
- **R0 (done)**: the skeleton plus three read-only endpoints
  (`GET /health`, `GET /api/positions`, `GET /api/positions/{id}`), 98 tests,
  HEAD `b262c33`.
- **W1 (this milestone)**: the 15 write/read routes of the positions-write,
  candidate, conversation, message and send-record families. **18 routes are
  served in total** (231 tests, R0's 98 included); the remaining 50 `/api`
  routes stay mapped to W2–W6.
- **Evidence**: `docs/contract-baseline/w1-python.json` (captured from a running
  Python baseline) and `w1-rust.json` (captured from the Rust port against its
  own copy of the same seed), compared by `scripts/contract_diff.py`, which also
  compares every row of the eight business tables afterwards. The R0 pair
  (`positions-python.json` / `positions-rust.json`) is kept as the earlier
  read-only record.

### 1.1 Scope and exclusions under baseline drift

The 68 is the count at the **frozen mirror** `/mnt/o/ica` @ `d39e321`. ICA's
main checkout has since gained a browser subsystem (`d96bb05`, six commits,
34 routes under `/api/browser/v1/` + 10 `browser_*` tables; uncommitted
BROWSER-04 work adds 6 more routes and 2 more tables). The non-browser route
set is **measured identical** — 68 → 68, `removed: 0` — so the wave plan is
unchanged, and the browser subsystem is **excluded from this migration**:

- **What is excluded**: every `/api/browser/v1/*` route (34 committed,
  6 more uncommitted) and every `browser_*` schema object (10 committed
  tables, 2 more uncommitted, plus their indexes).
- **Why** (ICA's own architecture documents, line numbers re-verified by
  `sed -n` on 2026-11-18): `browser-architecture-r1.md:229` "不迁移 Rust";
  `browser-implementation-breakdown-r1.md:28` and `:194` "不得提出 Rust
  迁移"; local-admin-cloud-management-architecture-r1.md §20.3 (line 688)
  "不构成 Python → Rust 迁移理由". The subsystem is an out-of-process Python
  sidecar (browser_bridge / connector / native host) + Playwright, not part
  of the 68-route CRUD core.
- **How the gates express it** (added in W1.6, self-tested): `scripts/
  check_endpoint_map.py` strips `--exclude-prefix` routes (default
  `/api/browser/`) and prints their count; `--expect-excluded N` fails if the
  count drifts, so the prefix list cannot silently widen. `scripts/
  compare_baseline_schema.py` strips `--exclude-table` objects (default
  `browser_*`, owner-table aware for indexes) and prints their count.
  `scripts/check_scope.py` runs both against the frozen mirror plus the two
  self-tests; it is an audit tool and stays out of `scripts/check.py`
  (which must run without a Python environment).
- **Measured arithmetic** (all measured 2026-11-18 on copies, never on the
  mirrors): frozen baseline = 20 tables (19 business/identity +
  `alembic_version`) × 66 indexes; `d96bb05` = SQLAlchemy metadata 29 tables
  (19 + 10 `browser_*`), alembic-upgraded DB 30 tables × 107 indexes (41 on
  `browser_*`); worktree with BROWSER-04 = metadata 31, alembic head 32
  tables × 121 indexes (55 on `browser_*`). Excluding `browser_*` collapses
  every row back to 20 × 66 → IDENTICAL.
- **Known sharp edge**: BROWSER-04 adds `POST /api/imports/{session_id}/
  confirm-candidate` — out of scope but **outside** the `/api/browser/`
  prefix, so the gate correctly reports it MISSING. Do not widen the prefix
  to hide it (that would shadow W4's real import routes); it is covered by
  the re-anchor decision instead.
- **Re-anchor procedure** (only with explicit user authorisation naming the
  target commit): ① re-run the two gates against the new mirror and update
  `--expect-excluded` / `--expect-excluded-tables`; ② re-run the full
  `contract_verify.sh` for the business 68; ③ update the numbers in this §1
  and in [`rust-migration-scope-20261118.md`](rust-migration-scope-20261118.md);
  ④ record the decision there.
- **The frozen mirror is an agreement, not a mechanism** (incident
  2026-11-18 22:05:39Z): a parallel session committed `95edb8d` in
  `/home/bryan/ica` at 22:00 and then fast-forwarded `/mnt/o/ica` to the same
  commit five minutes later, so the mirror stopped being frozen without any
  re-anchor decision. Measured afterwards: live `/api` = **112** routes of
  which **39** under `/api/browser/`, against the documented 68. The failure
  mode is misleading — `contract_verify.sh` still reported
  `185/185 cases matched, 0 failure(s)` (the W3 behaviour had not changed) and
  failed *only* on `git status: DIRTY` → exit 1, which reads like
  "clean up some uncommitted files" rather than "the baseline moved".
  Restored with `git checkout -- .` + `git reset --hard d39e321`, after first
  confirming the fast-forwarded commit still exists in `/home/bryan/ica` so
  nothing was lost; re-measured 68 routes / 0 browser, `status` clean,
  `ica.db` sha256 `466aa3fc…18e1`, and `contract_verify.sh` back to exit 0.
  **Therefore: verify `git -C /mnt/o/ica rev-parse --short HEAD` is `d39e321`
  before starting any wave, and treat a route count other than 68 (browser
  count other than 0) as a drifted baseline rather than a code defect.**

## 3. Waves and acceptance criteria

Every wave uses the same gate; only the endpoint set differs.

**Gate** (all must hold before a wave is called done):

1. `scripts/contract_capture.py` against a fresh Python baseline and against the
   Rust service, both on the **same seeded database**, then
   `scripts/contract_diff.py` → `N/N cases matched, 0 failure(s)`.
2. The wave's cases include: default list, pagination boundaries (`limit` min/
   max/over), `offset` past the end, each filter flag, search hit/miss/case/
   whitespace, 404, and every 422 the Python query/payload validation produces.
3. `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`,
   `cargo test` green, with the real test count quoted.
4. Read-path waves must open the baseline database with
   `?mode=ro&immutable=true` and leave `sha256sum ica.db` unchanged.
5. Write-path waves run against a **copy** of the baseline database; the
   baseline itself is never opened read-write.

| Wave | Content | Extra acceptance |
| --- | --- | --- |
| W1 | positions writes (POST/PATCH/DELETE), candidates, conversations, messages, timeline, send-records | Write schemas validated before the first write (no data-corruption path); `PATCH` rejects explicit `null` on NOT NULL columns with 422, not 500 |
| W2 | follow-ups (full state machine), policy, dashboard | The 12-state `FollowUpTaskStatus` machine matches Python transition-by-transition; `means_contacted` / `is_closed` semantics pinned by tests |
| W3 | drafts, draft-groups, context preview, AI generation entry point | AI calls go through a port; the service still boots with no API key (`ai_enabled=false`, 503 on the AI path) |
| W4 | imports preview/confirm/reject, export, import, OCR | Import validates the whole batch before writing (atomic rejection). Preview writes only `import_sessions` (+1), `import_records` (+1) and one `import.previewed` audit — it never writes business tables (`candidates`/`messages` unchanged); see `w4-python-facts.md` §1 for the measured row deltas |
| W5 | settings, ai-key, ai-egress consent, audit-events, backups, AI config/usage/budget | Secret values are never echoed or logged; backup/restore drill documented before implementation |
| W6 | auth (register/login/refresh/logout/me), shares | Refresh-token rotation is single-use and concurrency-safe; local mode stays default |
| W7 | cutover: dual-run, then Rust-only | Parity telemetry for a full week of real traffic; documented rollback to Python |

### 3.1 W1 measured on the Python baseline

The W1 rows above are only meaningful if the "Python behaviour" they are
compared against is measured, not assumed. Three facts were re-measured against
the running baseline (`/mnt/o/ica` @ `d39e321`) with the shared seed, and the
captures in `docs/contract-baseline/` are the record:

| Observation | Python (measured) | Why it matters |
| --- | --- | --- |
| `GET /api/messages?limit=2` | `total = 2` (5 rows exist) | `total = min(real_total, limit + offset)`, so the envelope's count cannot be used to compute page count and `has_more` is almost always `false`. Declared as **IMP-1**. |
| `PATCH /api/positions/{id}` with `{"name": null}` or `{"archived": null}` | **500** `internal_error` | The pydantic schema allows `None`, the service assigns it, and SQLite rejects the NOT NULL constraint inside `commit()`; the client cannot tell a bad request from a server crash. Declared as **IMP-2**. |
| `total` semantics across the five lists | positions / candidates / conversations / send-records = real count; messages truncated | One `Page` envelope with two different meanings. Declared as **IMP-3**. |

## 4. Layering rules (compile-enforced)

```
ica-server → ica-api + ica-infra → ica-application → ica-domain
```

| Crate | May depend on | Must not depend on |
| --- | --- | --- |
| `ica-domain` | `chrono` | axum, sqlx, tokio, hyper, any I/O |
| `ica-application` | `ica-domain`, `async-trait`, `chrono` | axum, sqlx, tokio, hyper |
| `ica-infra` | `ica-application`, `ica-domain`, `sqlx`, `tokio`, `async-trait` | axum |
| `ica-api` | `ica-application`, `ica-domain`, `axum`, `serde` | sqlx (the HTTP layer never writes SQL) |
| `ica-server` | `ica-api`, `ica-infra`, `axum`, `tokio` | — (composition root) |

This is enforced two ways, and neither depends on discipline:

1. **By the compiler.** A forbidden dependency is not in the crate's
   `Cargo.toml`, so `use sqlx::…` inside `ica-domain` does not compile. There is
   no allow-list to forget to update.
2. **By `scripts/check.py`**, which runs `cargo metadata --no-deps` and fails if
   `ica-domain` or `ica-application` lists axum / sqlx / tokio / hyper (a
   transitive path would not compile either, but the direct check gives a clear
   message).

## 5. Coexistence with Python

R0–W6 run **both** services side by side:

- **Same database, one writer.** Python stays the only writer until a wave has
  passed its contract diff; the Rust service opens the database
  `?mode=ro&immutable=true` for read waves.
- **Dual-run**: the same request is issued to both services and the normalised
  JSON is diffed (`scripts/contract_diff.py`). This is the only definition of
  "compatible" used here.
- **Gray routing** (from W1): the desktop shell points at the Rust service for
  the endpoints that wave owns, and at Python for everything else. Both listen
  on loopback; the shell picks by a `backend_base_url` setting, so a rollback is
  a setting change, not a redeploy.
- **Rollback**: switch the setting back to the Python port. The database is
  shared and additive, so no data migration is needed for a rollback — but a
  wave that adds a column must be reverted by an Alembic downgrade, which is why
  schema changes get their own review.
- **Retirement** (W7): Python is stopped only after a full week of Rust-only
  parity on real traffic.

## 6. R0/W1 scope boundaries (what these milestones do *not* do)

Served today (18 routes):

- `GET /health`, `GET /api/positions`, `GET /api/positions/{id}` (R0);
- `POST/PATCH/DELETE /api/positions/{id}`, `GET/POST /api/candidates`,
  `GET/PATCH/DELETE /api/candidates/{id}`,
  `GET/POST /api/conversations`, `GET/POST /api/messages`,
  `GET /api/candidates/{id}/timeline`, `GET/POST /api/send-records` (W1).

Not served yet, and deliberately out of scope for W1:

- follow-ups and dashboard (W2), drafts and AI (W3), imports/OCR/export (W4),
  settings/audit-events/backups (W5), auth and shares (W6), the `GET /` welcome
  string, packaging, the desktop shell and any frontend change.

- **Tenant/owner scoping is not modelled.** In `local` mode (the default) the
  Python `access.scope_*` helpers return the statement unchanged, and every row
  W1 writes is stamped with the V1.0 local owner/tenant. Multiuser scoping
  arrives with W6 auth; until then the Rust service must not be run in
  `multiuser` mode.

## 7. Known deltas and how they are handled

| Delta | Handling |
| --- | --- |
| Timestamps | Python (`as_utc` + pydantic) renders `2026-11-10T09:00:00Z`, and six fractional digits **only when non-zero** (`...T12:00:00.500000Z`). Verified against a live server; implemented in `ica-api/src/dto.rs::format_utc`. |
| `422 details.errors` | The list is pydantic-specific. `contract_diff.py` compares status + `error.code` + `error.message` + the set of `details` keys, and ignores the per-provider error list. The Rust side emits the same four keys (`type`, `loc`, `msg`, `input`) with pydantic's JSON types: `loc` array indices are NUMBERS and `input` keeps the original JSON value (a string stays a string, `null` stays null) — the independent W4 audit (LWW P1-1) measured the earlier double-encoded/string-indexed rendering as a real divergence, and it is fixed with regressions in `w4_reaudit_regressions.rs`. The `import_validation_error` list is an ARRAY of `{table, index, field, message, value}` problems, matching the baseline's `details={"errors": problems}`. |
| `GET /` | Not implemented (not part of the API surface). |
| Read-only opening | `?mode=ro` (without `immutable`) still updates the `-shm` sidecar's **mtime** of a WAL database — measured, and the cause is *any* such open, including `scripts/compare_baseline_schema.py`; the file's **content sha256 does not change**. The Rust service opens the baseline with `?mode=ro&immutable=true`, which leaves `ica.db`, `-wal` and `-shm` byte- and mtime-identical. |
| Sort order without tie-break | Every list sorts by a single column (`ORDER BY p.created_at DESC`, `updated_at DESC`, …) with no secondary key, so rows sharing a timestamp have SQL-undefined order. Both sides run the same SQL over the same rows, so the capture is currently stable — but that is agreement by coincidence, not by contract. Adding a tie-break (e.g. `p.id`) would change response order and must be registered as an IMP with frontend sign-off first (audit finding F-11). |
| Baseline emptiness | The current baseline database contains 0 positions, so the read-only proof is the startup self-check (20 tables) plus a 200 from `/api/positions`; contract parity is proven against the seeded database instead. |

### 7.1 Declared improvements (W1)

The user's instruction for W1 allows fixing defects in the baseline, provided
every difference is declared here **and** asserted with its concrete value on
both sides by `scripts/contract_diff.py` (section `improvements:`). A difference
outside this table fails the comparison.

| # | Endpoint | Python value (measured) | Rust value | Reason | Frontend impact |
| --- | --- | --- | --- | --- | --- |
| **IMP-1** | `GET /api/messages` → `total` | `total = min(real_total, limit + offset)`. With 5 matching rows: `?limit=2` → `total=2`, `has_more=false`; `?limit=2&offset=1` → `total=3` | `total` = the real number of matching rows, independent of the window (`?limit=2` → `total=5`, `has_more=true`) | `total` means "rows before paging"; a truncated value makes the page count uncomputable and `has_more` almost always false | **None.** No code under `frontend/src` reads `Page.total` / `Page.has_more` except the type definition in `types.ts` (verified by grep; only tests reference them) |
| **IMP-2** | `PATCH /api/positions/{id}` with an explicit `null` on a NOT NULL column | `{"name": null}` → **500** `internal_error`; `{"archived": null}` → **500** `internal_error` | **422** `validation_error` with the same envelope as every other validation failure | A 500 means "unhandled exception": the client cannot tell a bad request from a server crash, and §3 already requires 422 for a rejected payload | **None positive, none negative.** The frontend never sends `null` for these fields; a bug that did would now show a validation message instead of a generic 500 |
| **IMP-3** | The five list endpoints → `total` | positions / candidates / conversations / send-records report the real total; messages reports the truncated one | All five report the real total | One `Page` envelope must mean one thing, or a client cannot write generic paging code | **None** (same grep as IMP-1) |
| **IMP-4** | The five list endpoints with `offset` beyond `u64::MAX` (R0 audit F-03) | **200** with an empty page; Python integers are unbounded, so the offset is echoed back as-is, however large | **422** `validation_error` / `int_parsing` | The page envelope echoes `offset` as a JSON number typed `usize`, and nothing wider than `u64::MAX` (≈1.8e19) fits — the echo is impossible. Within that threshold the values match exactly (`?offset=9223372036854775808`, past `i64::MAX`, answers 200 on both sides) | **None.** An offset above 1.8e19 is scanner noise; real clients page inside `u64` |

`IMP-4` is registered from the R0 audit (2026-11-17), not as a W1 improvement:
the port accepted nothing past `i64::MAX` before it, and `u64::MAX` is the
widest echoable threshold. The same audit closed the other parser/router gaps —
repeated query keys now keep the **last** occurrence like Starlette (no
plain-text 400), booleans are no longer whitespace-trimmed, `405` carries the
JSON envelope, `HEAD` on a served route answers 405, and trailing-slash paths
307-redirect with method and query preserved. Each is pinned by a named case in
`contract_capture.py`.

Deliberately **not** changed, to keep the wave's scope honest:

- `GET /` keeps its Python behaviour (not implemented at all — it is not part of
  the API surface);
- no endpoint is added that Python does not have;
- the per-field text inside `details.errors` for the ROUTE-level validators
  (`body.rs`/`query.rs`) is pydantic-shaped but not guaranteed verbatim (the
  comparison compares `code`, `message` and the `details` key set, by design);
  the IMPORT validator's row problems (`_position_problems`) ARE reproduced
  verbatim, messages included, because the audit probes compare them textually;
- timestamps keep the `...T09:00:00Z` rendering from R0;
- no existing field name, type or required-ness changes, and no sort order or
  error-code enum changes.

### 7.1c Implementation optimizations (W3)

| # | Optimization | Python value | Rust value | Reason | Frontend impact |
| --- | --- | --- | --- | --- | --- |
| **OPT-3** | Draft list paging pushed into SQL | reads every matching row, then slices `[offset : offset + limit]` | `SELECT COUNT(*)` for `total` plus `LIMIT ? OFFSET ?` for the window, same filter and `ORDER BY created_at DESC` | a page no longer reads the whole table | **None** — identical items in identical order, identical envelope |
| **OPT-4** | Group supersede runs in one transaction | loops over the group and commits each superseded draft separately | the whole loop runs in a single transaction (`BEGIN` … `COMMIT`), so a failure leaves no half-superseded group | the baseline can leave the group half-rejected if one row's write fails; the port cannot | **None** — the same rows end up `rejected` with the same `rejected_at` |

The per-row work is deliberately **not** collapsed into one statement: every
superseded draft needs its own `draft.rejected` audit event, so the port
issues one `UPDATE` plus one audit insert per row, exactly like the baseline —
inside one transaction instead of one commit each.

The audit trail is preserved either way: `draft.rejected` /
`Draft rejected as superseded by a group member` with the
`superseded_by` / `reason` metadata is written for every superseded row, and
the `generated_drafts` table is compared row by row by the contract diff.

### 7.2 Implementation optimizations (W1)


These change *how* a value is produced, never the value. Each is covered by the
contract comparison (items, `total`, `offset`, `limit`, `has_more` and every
stored row must still match Python exactly).

| # | Optimization | Python value | Rust value | Reason | Frontend impact |
| --- | --- | --- | --- | --- | --- |
| **OPT-1** | Conversation `message_count`: N+1 read per conversation | One `list_messages(conversation_id=…, limit=1000)` per conversation; the value is `min(real_count, 1000)` | One `GROUP BY conversation_id` aggregate joined into the list query; the value is `min(real_count, 1000)` (the 1000 cap is reproduced with `CASE WHEN cnt > 1000 …`) | The number is identical, but the baseline issues one extra query per row on the page (`ica-infra/conversations.rs`) | **None** — same integers in the same fields |
| **OPT-2** | List paging pushed into SQL | Reads every matching row, then slices `[offset : offset + limit]`; `items` / `total` / `has_more` as computed from that slice | `SELECT COUNT(*)` for `total` plus `LIMIT ? OFFSET ?` for the window, same filter and `ORDER BY`; same `items` / `total` / `has_more` | A page no longer reads the whole table; the diff compares `items[].id` order for all five lists (`ica-infra/repository.rs`, `candidates.rs`, `conversations.rs`, `send_records.rs`) | **None** — identical items in identical order, identical envelope |

`positions` gets the same treatment: `PositionRepository` has a default `page()`
that slices in memory (so a test double only implements `list` + `find`), and
the SQLite adapter overrides it with `COUNT(*)` + `LIMIT/OFFSET` — which is what
the running service calls.

`PATCH` is a read-modify-write of the whole row (the ORM's own shape), so a
patch cannot silently write a column the request never mentioned — and it keeps
the write path to two statements without dynamic SQL.

### 7.3 How `contract_diff.py` normalises

Normalisation is symmetric on both sides and never hides a value:

- **UUIDs** are random per server, so every 36-character UUID is replaced by
  `<uuid:N>`, numbered by first appearance (cases in sorted-name order, then the
  row dump). A row seen in a response and in the table dump gets the same
  placeholder, which is what makes `audit_events.entity_id` a real assertion.
- **Timestamps at or after the capture's own `started_at`** (minus 60 s) become
  `<now>`: they are "the moment this request ran" on both sides. Seeded
  timestamps are in the past and stay literal, so they are compared exactly.
- **422 bodies** collapse to `code` + `message` + the sorted `details` key set.
- **`Location` headers** are reduced to `path?query` before comparing: the
  absolute URL embeds each side's own port. `content_type` is compared for
  every case — a plain-text rejection body is the F-02 failure mode, so the
  media type is part of the contract.

Everything else — every field, every row of the eight business tables, the
audit metadata (parsed), `messages.content_hash`, row counts — is compared
exactly.

### 7.4 Baseline side effect reproduced on purpose

Deleting a position clears `candidates.position_id` (FK `ON DELETE SET NULL`).
Python's ORM also nulls the child through the relationship, which fires the
`updated_at` `onupdate` hook **once per row**; a bare SQLite FK action would
leave `updated_at` untouched. The Rust delete therefore stamps the affected
candidates in the same transaction, one microsecond apart, in rowid order.

Without that, a candidate that lost its position would sort differently in the
next `updated_at DESC` listing — a visible difference the comparison caught.
The scenario deletes a position with a single candidate on purpose: Python's
per-row `utcnow()` can land two rows in the same microsecond, which would make
the *baseline itself* non-deterministic and the ordering untestable.

One command seeds, runs both services on **separate copies** of that seed
(the scenario writes), captures both sides and diffs responses plus final rows:

```

The implementation is `scripts/contract_verify.py`; the shell file is a wrapper
around it.

Last run: **`185/185 cases matched, 0 failure(s)`** (W3), including
`PASS db.<table>` for all nine business tables — the post-scenario state of

> **The Python side must be isolated from the operator's stored credential.**
> `app/config.py` ends with `apply_stored_secrets(settings)`, which overlays
> the OS credential store (`<data dir>/secrets/ai_api_key.secret`) onto the

> isolates it: `app/paths.py::default_data_dir` honours that variable). A
