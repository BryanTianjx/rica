# Rust migration contract — ICA Personal backend

This document is the map for moving the ICA Personal backend HTTP/data plane
from Python (FastAPI + SQLAlchemy) to Rust (axum + sqlx), one wave at a time.

- **Contract authority**: the Python baseline at `/mnt/o/ica` @ `d39e321`. Where
  this document and the Python code disagree, the Python code wins until a wave
  explicitly changes it.
- **R0 (this milestone)**: the skeleton plus three read-only endpoints. Waves
  W1–W7 below are *not* implemented yet.
- **Evidence**: `docs/contract-baseline/positions-python.json` (captured from a
  running Python server) and `positions-rust.json` (captured from the Rust
  server against the same database). `scripts/contract_diff.py` compares them.

## 3. Waves and acceptance criteria

Every wave uses the same gate; only the endpoint set differs.

**Gate** (all must hold before a wave is called done):

1. `scripts/contract_capture.py` against a fresh Python baseline and against the
   Rust service, both on the **same seeded database**, then
   `scripts/contract_diff.py` → `N/N cases matched, 0 failure(s)`.
2. The wave's cases include: default list, pagination boundaries (`limit` min/
   max/over), `offset` past the end, each filter flag, search hit/miss/case/
   whitespace, 404, and every 422 the Python query/payload validation produces.
3. `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`,
   `cargo test` green, with the real test count quoted.
4. Read-path waves must open the baseline database with
   `?mode=ro&immutable=true` and leave `sha256sum ica.db` unchanged.
5. Write-path waves run against a **copy** of the baseline database; the
   baseline itself is never opened read-write.

| Wave | Content | Extra acceptance |
| --- | --- | --- |
| W1 | positions writes (POST/PATCH/DELETE), candidates, conversations, messages, timeline, send-records | Write schemas validated before the first write (no data-corruption path); `PATCH` rejects explicit `null` on NOT NULL columns with 422, not 500 |
| W2 | follow-ups (full state machine), policy, dashboard | The 12-state `FollowUpTaskStatus` machine matches Python transition-by-transition; `means_contacted` / `is_closed` semantics pinned by tests |
| W3 | drafts, draft-groups, context preview, AI generation entry point | AI calls go through a port; the service still boots with no API key (`ai_enabled=false`, 503 on the AI path) |
| W4 | imports preview/confirm/reject, export, import, OCR | Import validates the whole batch before writing (atomic rejection), and never writes on preview |
| W5 | settings, ai-key, ai-egress consent, audit-events, backups, AI config/usage/budget | Secret values are never echoed or logged; backup/restore drill documented before implementation |
| W6 | auth (register/login/refresh/logout/me), shares | Refresh-token rotation is single-use and concurrency-safe; local mode stays default |
| W7 | cutover: dual-run, then Rust-only | Parity telemetry for a full week of real traffic; documented rollback to Python |

## 4. Layering rules (compile-enforced)

```
ica-server → ica-api + ica-infra → ica-application → ica-domain
```

| Crate | May depend on | Must not depend on |
| --- | --- | --- |
| `ica-domain` | `chrono` | axum, sqlx, tokio, hyper, any I/O |
| `ica-application` | `ica-domain`, `async-trait` | axum, sqlx, tokio, hyper |
| `ica-infra` | `ica-application`, `ica-domain`, `sqlx`, `tokio`, `async-trait` | axum |
| `ica-api` | `ica-application`, `ica-domain`, `axum`, `serde` | sqlx (the HTTP layer never writes SQL) |
| `ica-server` | `ica-api`, `ica-infra`, `axum`, `tokio` | — (composition root) |

This is enforced two ways, and neither depends on discipline:

1. **By the compiler.** A forbidden dependency is not in the crate's
   `Cargo.toml`, so `use sqlx::…` inside `ica-domain` does not compile. There is
   no allow-list to forget to update.
2. **By `scripts/check.sh`**, which runs `cargo metadata --no-deps` and fails if
   `ica-domain` or `ica-application` lists axum / sqlx / tokio / hyper (a
   transitive path would not compile either, but the direct check gives a clear
   message).

## 5. Coexistence with Python

R0–W6 run **both** services side by side:

- **Same database, one writer.** Python stays the only writer until a wave has
  passed its contract diff; the Rust service opens the database
  `?mode=ro&immutable=true` for read waves.
- **Dual-run**: the same request is issued to both services and the normalised
  JSON is diffed (`scripts/contract_diff.py`). This is the only definition of
  "compatible" used here.
- **Gray routing** (from W1): the desktop shell points at the Rust service for
  the endpoints that wave owns, and at Python for everything else. Both listen
  on loopback; the shell picks by a `backend_base_url` setting, so a rollback is
  a setting change, not a redeploy.
- **Rollback**: switch the setting back to the Python port. The database is
  shared and additive, so no data migration is needed for a rollback — but a
  wave that adds a column must be reverted by an Alembic downgrade, which is why
  schema changes get their own review.
- **Retirement** (W7): Python is stopped only after a full week of Rust-only
  parity on real traffic.

## 6. R0 scope boundaries (what this milestone does *not* do)

- Only `GET /health`, `GET /api/positions`, `GET /api/positions/{id}`.
- No write paths, no auth, no AI/OCR, no frontend change, no packaging.
- **Tenant/owner scoping is not modelled.** In `local` mode (the default) the
  Python `access.scope_position_query` returns the statement unchanged, so the
  two services agree today. Multiuser scoping arrives with W6 auth; until then
  the Rust service must not be run in `multiuser` mode.

## 7. Known deltas and how they are handled

| Delta | Handling |
| --- | --- |
| Timestamps | Python (`as_utc` + pydantic) renders `2026-11-10T09:00:00Z`, and six fractional digits **only when non-zero** (`...T12:00:00.500000Z`). Verified against a live server; implemented in `ica-api/src/dto.rs::format_utc`. |
| `422 details.errors` | The list is pydantic-specific. `contract_diff.py` compares status + `error.code` + `error.message` + the set of `details` keys, and ignores the per-provider error list. The Rust side still emits a structurally similar list (`type`, `loc`, `msg`, `input`). |
| `GET /` | Not implemented (not part of the API surface). |
| Read-only opening | `?mode=ro` alone still updates the `-shm` sidecar of a WAL database. The baseline proof therefore uses `?mode=ro&immutable=true`, which leaves `ica.db`, `-wal` and `-shm` byte- and mtime-identical. |
| Baseline emptiness | The current baseline database contains 0 positions, so the read-only proof is the startup self-check (20 tables) plus a 200 from `/api/positions`; contract parity is proven against the seeded database instead. |

## 8. Re-running the comparison

```bash
# 1. Schema + seed (shared by both sides)
python3 scripts/seed_contract_db.py --out /tmp/ica-contract/seed.db

# 2. Python baseline (copy without .env/.venv; uses the baseline interpreter)
rsync -a --exclude '.venv' --exclude '.env' --exclude '__pycache__' \
  --exclude 'ica.db*' /mnt/o/ica/backend/ /tmp/ica-py-baseline/
cd /tmp/ica-py-baseline
env -u PYTHONPATH -u AI_API_KEY PYTHONDONTWRITEBYTECODE=1 \
  DATABASE_URL="sqlite:////tmp/ica-contract/seed.db" \
  /mnt/o/ica/backend/.venv/bin/python -m uvicorn app.main:app --port 8010 &

# 3. Rust service on the same database, read-only
cd /mnt/o/ICA-RUST
DATABASE_URL="sqlite:////tmp/ica-contract/seed.db?mode=ro" PORT=8011 cargo run -p ica-server &

# 4. Capture and diff
python3 scripts/contract_capture.py --base-url http://127.0.0.1:8010 \
  --out docs/contract-baseline/positions-python.json
python3 scripts/contract_capture.py --base-url http://127.0.0.1:8011 \
  --out docs/contract-baseline/positions-rust.json
python3 scripts/contract_diff.py \
  --python docs/contract-baseline/positions-python.json \
  --rust docs/contract-baseline/positions-rust.json
```
